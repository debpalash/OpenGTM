# Kernel microbenchmarks (M0 evidence)

These are **in-process microbenchmarks**. They exclude network, database,
queueing and everything else in a real enrichment or scrape; they measure
only the cost of the computation and of crossing into the WebAssembly
sandbox. Use them to decide where kernels pay off, not as throughput claims.

## Commands

```bash
cd apps/server && go test -run '^$' -bench . -benchmem -count 10 ./internal/kernels/
cd crates && cargo run --release --example timing           # native Rust, no wasm
uv run python crates/opengtm-kernels/parity/bench_python.py  # Python baseline
```

Inputs are identical across the three: `testdata/bench_corpus.json` (1,000
realistic domains, emails, phones and names, generated by `bench_python.py
--write-corpus`) and the team-page extract fixture (`testdata/team_page.html`,
2.5 KB, 4 records, 8 fields including one regex). The Python extraction is
the BeautifulSoup code path the Python scrapers use (`html.parser` in the
leadgen scrapers, `lxml` in `services/scraper.py`), written to produce the
same records; the script checks that its output equals the kernel fixture.

## What the numbers say

1. **The sandbox boundary, not the computation, dominates small calls.** A
   single `normalize_domain` costs 263 ns natively and about 2.2 µs through
   the Go host (three guest calls plus JSON on both sides). Through the
   Extism Go SDK it costs about 31 µs, because each call routes several
   runtime functions through freshly created wazero function objects (about
   256 KB of Go allocation per call). That measured overhead is why the Go
   host uses the direct ABI; the plugin platform should expect the same
   per-call cost for Extism plugins and batch accordingly.
2. **Interruptibility is expensive.** wazero's `WithCloseOnContextDone`
   compiles termination checks into guest code. With them, extraction is
   about 3x slower (1,074 vs 352 µs), and a 1k domain batch was about 4x
   slower in an earlier run (8.2 vs 1.9 ms, on the parity corpus before the
   allocation work in commit `98948e1`). The Go package
   therefore runs normalizers (linear in bounded input) without checks and
   extraction (whose CSS cost can grow with document depth) with them.
3. **Wasm runs about 3x slower than native** for these kernels once boundary
   costs are subtracted (for example domain: 997 − 121 JSON ≈ 876 ns in the
   guest vs 334 ns native). `opt-level=3` was 13–24% faster than `"s"` for
   about 9.5% more size (2.24 MB); the release profile keeps `"s"` as
   specified. Pinning `idna_adapter` to its ASCII-only release would save
   130 KB (6%) but break IDN base URLs, so it was not done.
4. **Against Python:**
   - Domain normalization is about 2x faster through the kernel than
     Python's `urlparse`-based function, and native Rust is 6x faster.
   - Email, phone and name normalization are trivial string operations. Python
     is already as fast as or faster than the kernel call (email 127 vs 531,
     name 216 vs 933 ns/value); even native Rust only matches Python because
     JSON framing costs more than the work. Moving these alone to Rust/wasm
     buys nothing. They pay off only inside a larger kernel (dedup or entity
     matching over whole batches) or as plain Go code in the coordinator.
   - Extraction of a small page costs about the same as BeautifulSoup per
     call when interruptible (1.07 vs 1.04–1.18 ms) and 3x less without
     checks, but it runs in parallel across cores inside one process (about
     10,400 pages/s on this machine) while the Python scraper is limited to
     one core per process. Native Rust is about 11x faster than
     BeautifulSoup, so most of the remaining gap is the sandbox.
5. **Fixed costs** are small next to network fetches: a new instance costs
   0.1–0.2 ms and compiling both pools about 0.3 s at startup.

## Not measured

- Large documents as a benchmark (the 9 MB, 10,000-record extraction in
  `TestLargeDocument` takes about 1.7 s in the interruptible pool, indicative
  only), memory per instance under load, and p99 latency under contention.
- `wasm-opt -Oz` (not installed on the benchmark machine).
- End-to-end enrichment or scrape throughput, which the plan's M0 harness
  covers.
