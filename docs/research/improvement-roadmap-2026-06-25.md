# Yupcha Improvement Roadmap (synthesized, skeptic-corrected)

> OSS, AGPLv3, self-hostable Clay alternative. This roadmap merges five research dimensions, applies the skeptic audit's corrections, and drops the discard list. Every item was cross-checked against the actual codebase (paths cited are real: `apps/api/services/workbook/research_column.py`, `apps/api/services/agent/autopilot.py`, `apps/api/services/leadgen/enrichment/cache.py`, `apps/api/services/queue_service.py`, `apps/api/services/leadgen/llm.py`, `apps/api/services/workbook/prompt_guard.py`, `apps/mcp/server.py`).

## Executive summary

Yupcha already owns the hard parts of a Clay alternative: provider waterfalls, a durable Postgres job queue (`FOR UPDATE SKIP LOCKED` + heartbeat reaping), a bounded-concurrency provider runner, a Claygent-equivalent research column, an autopilot chat with a real human-in-the-loop approval gate, signal *detection*, an SMTP sequencer, an MCP server, a credit ledger with pre-run cost projection, and a unique **spend-before-you-run + BYO-keys + self-host + no-data-resale** posture. The gaps are not "more capability" — they are **closed loops, correct surfaces, cost discipline, and trust artifacts.**

Six themes drive everything below:

1. **Cost is the fastest ROI.** The Claude path goes through the generic provider call with **no prompt caching and no Message Batches** (verified in `llm.py`). Turning these on cuts the dominant LLM line item ~50–90% on the per-row workload that defines the product. This is the cheapest high-impact work available and should ship first.
2. **Loops beat features.** Yupcha *detects* signals but never *acts* on them; the MCP server is *read-only*; the SMTP sequencer lacks deliverability infra. Wiring detection → enrichment → sequence → send (gated by the existing spend ceiling) converts a "batch enrichment spreadsheet" into a "GTM execution system."
3. **The agent is built on the lowest-common-denominator path.** Claygent emulates tool-use via `extract_json` (hand-rolled ReAct, `MAX_STEPS_CAP=6`, no citations); the autopilot planner is pure `_FIELD_PATTERNS` regex. Native Claude tool-use + an LLM planner are step-changes.
4. **Free, authoritative, keyless registry data is the open moat.** SEC EDGAR (funding/intent), GLEIF (corporate hierarchy), Companies House (decision-makers), and job-posting tech intent are data Clay/Apollo *charge for* and a self-hosted AGPL tool can ship for $0 marginal cost.
5. **Self-hostability is a structural advantage, not just a license.** Unlimited in-house SMTP verification (Reacher), unlimited self-hosted technographics, BYO proxies/keys with the bill shown, and an *open, reproducible* provider-accuracy benchmark are things Clay structurally cannot match.
6. **Defensible-by-design.** Encode the public-vs-authenticated scraping line and PII handling as policy, and surface license/freshness per fact — a trust artifact for EU/regulated buyers fleeing credit black-boxes and contributory-network resale.

**Sequencing:** Now = cost levers + correctness fixes that are nearly free given existing infra. 30d = the highest-leverage loops and the registry data tier. 60d = the heavier agentic/security and scale rearchitecture. 90d = deliverability hardening, write-capable MCP, and the differentiation surfaces.

Note on Claude API identifiers (skeptic correction, load-bearing): use `web_fetch_20250910` (there is **no** `web_fetch_20260209`) and `web_search_20260318` (latest, with dynamic filtering). Message Batches support **up to 100,000** requests per batch (not 10,000). Prompt-cache reads bill at ~10% of input.

## Enrichment quality & accuracy

Yupcha has waterfalls, an eval harness, dedup, and is building SMTP verification + Hunter/Snov. The 2025–26 reality: raw SMTP is structurally unreliable (Gmail/Microsoft don't answer RCPT honestly; 13–28% of B2B domains are catch-all; greylisting 4xx misread as invalid). The winning architecture is **confidence-scored** (not binary) verification, **multi-source corroboration**, and verification as a **final gate**.

**Skeptic framing correction:** the "best verifier ~70%" ceiling is a *blended* number that includes catch-all (~17%) and anti-harvesting; honest-responding domains realistically hit 95–98%. Don't imply 70% is the ceiling for all mail — it's the argument *for* graded confidence.

### Incremental wins (ranked)
1. **Self-host Reacher (check-if-email-exists) as the SMTP tier with SOCKS5 proxy rotation** — impact **high**, effort **M**. Returns exactly the signal set needed (safe/risky/invalid/unknown, catch-all, disposable, role). Unlimited verifications at zero per-email cost — a structural win over Clay's metered verifier credits. Wire proxy rotation (the #1 reason naive SMTP fails) and special-case Gmail/Microsoft to fall through to corroboration. **Skeptic note:** Reacher is **dual-licensed (AGPL-3.0 OR commercial)**; Yupcha uses the AGPL path legitimately — state it as dual-licensed, not simply "free." Sources: https://github.com/reacherhq/check-if-email-exists , https://reacher.email/
2. **Confidence-scored verdicts (safe/risky/invalid/unknown + 0–100 score), not binary** — impact **high**, effort **S**. Extend the verify-status badge (efa0551) to a graded verdict + score so users threshold (e.g. send to ≥70) and sequencing deprioritizes risky addresses. 4xx greylist must never score as invalid. Sources: https://hunter.io/email-verification-guide/best-email-verifiers/ , https://www.mailercheck.com/articles/email-greylisting
3. **Verification as the final waterfall gate + early-stop on corroboration** — impact **high**, effort **M**. Verify last, not per-provider; stop once 2 sources corroborate AND verification passes (lift drops to 3–5% past the 4th provider); make provider order user-configurable and benchmark-seeded; record which provider supplied each accepted field. Drives bounce below the 3% threshold the new sender rules punish. Sources: https://www.unifygtm.com/explore/waterfall-enrichment-b2b-contact-data , https://www.cognism.com/blog/waterfall-enrichment
4. **Dynamic disposable detection (MX-cluster + domain-age + auth records)** — impact **medium**, effort **M**. Static lists decay to ~43% in a month (confirmed); keep the aggregate as a fast first pass, add MX-clustering, WHOIS recency, weak SPF/DKIM/DMARC, local-part entropy. All cheap server-side lookups, run unlimited because self-hosted. Sources: https://prospeo.io/s/disposable-email-detection , https://blog.castle.io/inside-the-infrastructure-behind-fake-signups-our-open-source-disposable-email-domain-list/
5. **libphonenumber normalization + optional HLR/line-type tier** — impact **medium**, effort **M**. Free offline parse/normalize/validate; optional BYO-key HLR for live subscriber status/line type (TCPA/SMS routing). Rounds out the four canonical waterfall metrics. Sources: https://www.abstractapi.com/guides/phone-validation/google-phone-number-validation , https://www.ipqualityscore.com/free-hlr-lookup
6. **Per-cell freshness TTLs + auto re-verification + job-change re-enrichment** — impact **medium**, effort **M**. Reuse PR A cell metadata (d82a697) to store verified-at + source; re-verify emails >90 days (decay ~3.6%/mo), show staleness, scheduled re-enrichment detects job changes. Sources: https://www.cleanlist.ai/blog/2026-01-22-b2b-data-decay-statistics , https://salesmotion.io/blog/b2b-data-decay-strategy
7. **MX + DMARC/SPF as quality signals (new sender ecosystem)** — impact **medium**, effort **S**. Missing MX = hard-invalid; auth-record presence corroborates disposable/quality scoring; since Nov 2025 valid-but-undeliverable-due-to-sender-policy is a real failure mode. Sources: https://www.proofpoint.com/us/blog/email-and-cloud-threats/clock-ticking-stricter-email-authentication-enforcements-google-start , https://powerdmarc.com/bulk-email-sender-requirements/

### Major bets (ranked)
1. **Public, continuous, reproducible provider-accuracy benchmark** — impact **high**, effort **L**. Extend `data/provider_eval` into a published benchmark: fixed ground-truth, segmented by size/geo, reporting match rate, accuracy, **false-positive rate** (the metric vendors hide), and unknown/catch-all share per provider; auto-order the waterfall from results. This is the single biggest thing Clay structurally cannot do — an open, auditable trust artifact that *also* self-optimizes data quality. Sources: https://www.dropcontact.com/email-finder-benchmark , https://www.unifygtm.com/explore/waterfall-enrichment-b2b-contact-data
2. **Probabilistic catch-all resolution via cross-source corroboration** — impact **high**, effort **L**. Never mark catch-all addresses valid; score from dominant email pattern, 2+ finder agreement, person-exists evidence, MX reputation; multi-probe to confirm accept-all; learn per-domain patterns. Attacks the dominant accuracy killer (13–28% of B2B) and reuses Yupcha's existing corroborated-fuzzy primitive. Sources: https://www.no2bounce.com/blog/how-to-verify-catch-all-emails-in-2026---complete-guide , https://billionverify.com/blog/catch-all-email-detection
3. **Splink (Fellegi-Sunter) explainable identity-resolution layer** — impact **high**, effort **L**. Upgrade dedup from heuristic fuzzy to unsupervised EM record linkage on DuckDB (no labels, ~1M records/minute, explainable per-field weights). Open-source, in-process (no new infra), transparent merges users can tune — a trust edge over Clay's black-box matching. Sources: https://www.robinlinacre.com/introducing_splink/ , https://pypi.org/project/splink/

## Browser automation & anti-bot

Detection splits into three independent layers (TLS/JA3, JS/headless, automation-protocol/CDP). No single tool wins; the answer is a **health-driven escalation ladder** with BYO proxies/solvers. Yupcha's self-host nature is the edge: ship the whole ladder built-in.

Apache-2.0 drop-in that patches the highest-signal CDP leaks (`Runtime.enable`/`Console.enable`, `navigator.webdriver`). **Must** run with `channel=chrome` + persistent context + `no_viewport`. Avoid rebrowser-playwright (same failures as vanilla since Sept 2024) and abandoned playwright-extra. Sources: https://github.com/Kaliiiiiiiiii-Vinyzu/patchright , https://ianlpaterson.com/blog/anti-detect-browser-benchmark-patchright-nodriver-curl-cffi/

Per-domain state machine: Tier 0 curl_cffi → Tier 1 patchright → Tier 2 nodriver/camoufox → Tier 3 solver/computer-use. Escalate on health signals (block/challenge/403/429 rates), keep IP+fingerprint stable per session then rotate, back-pressure on spikes. Cheap tiers handle ~80%+; this controls per-row cost. Sources: https://ianlpaterson.com/blog/anti-detect-browser-benchmark-patchright-nodriver-curl-cffi/ , https://scrapingant.com/blog/proxy-strategy-in-2025-beating-anti-bot-systems-without

## Scale & cost

Strong substrate already (Postgres queue with SKIP LOCKED + heartbeat reaping, bounded-concurrency runner, TTL'd cache, credit ledger with pre-run projection, logfire). Verified gaps: no Anthropic prompt caching/batches in app code; the enrichment cache is a **per-process SQLite file** (`cache.py` line 105); the worker runs **one job at a time per process** with a 1s poll; rate limiting is per-process; no per-provider cost/cache-hit/latency metrics; no in-flight spend breaker.

### Incremental wins (ranked)
1. **Anthropic prompt caching on Claygent + AI columns** — impact **high**, effort **S**. Mark the large invariant prefix (system + schema + instructions + few-shots) `cache_control: ephemeral`, keep per-row lead data outside the breakpoint. A run fires the same prefix across hundreds of rows in seconds → hit rate ~100% after row 1, ~90% input-token savings on the repeated portion. **The single cheapest high-impact change in this roadmap — ship first.** Sources: https://platform.claude.com/docs/en/build-with-claude/prompt-caching , https://introl.com/blog/prompt-caching-infrastructure-llm-cost-latency-reduction-guide-2025
2. **Move the enrichment cache to Postgres (shared across replicas)** — impact **high**, effort **M**. Promote `EnrichmentCache` from per-container SQLite to a Postgres table (same canonical key, TTL via expires_at, INSERT … ON CONFLICT); optional Redis read-through for hot keys. Today each replica re-pays providers for the same identity — a shared cache turns the biggest paid-provider lever into fleet-wide dedup-on-lookup. Sources: https://www.freecodecamp.org/news/how-to-use-postgresql-as-a-cache-queue-and-search-engine/ , https://richyen.com/postgres/2026/05/04/postgres_job_queue.html
3. **Centralize per-provider rate limiting with a Redis token-bucket** — impact **high**, effort **M**. Replace per-process 429 backoff with a distributed token-bucket keyed per provider (and per BYOK key) using the existing Redis; keep exponential-backoff-with-jitter as reactive fallback. Stops N replicas collectively blowing shared limits (avalanche 429s → empty cells). Sources: https://pypi.org/project/pyrate-limiter/ , https://pypi.org/project/redis-rate-limiters/
4. **LISTEN/NOTIFY wake-up to cut the 1s claim-poll latency** — impact **medium**, effort **S**. Keep SKIP LOCKED as the backbone; NOTIFY on enqueue, idle workers LISTEN, poll as fallback only (NOTIFY drops on disconnect, serializes under load, breaks behind transaction-mode PgBouncer). Matters once jobs are sharded (below). Sources: https://worker.graphile.org/ , https://nerdleveltech.com/postgres-listen-notify-job-queue
5. **OpenTelemetry GenAI cost/latency/cache-hit metrics** — impact **medium**, effort **M**. On top of logfire, record `gen_ai.*` attributes + derived `cost_usd` for LLM and paid-provider calls; export as spans + histograms so a self-hosted Grafana/Tempo dashboard shows cost-per-workbook, hit rate, p95, 429 rate. Makes billing auditable — an OSS advantage over opaque credits. Sources: https://opentelemetry.io/blog/2026/genai-observability/ , https://uptrace.dev/blog/llm-cost-monitoring
6. **In-flight spend circuit breaker at the worker** — impact **medium**, effort **M**. Extend the billing service from pre-run projection to a live accumulator (from the new cost metrics) that trips near a cap — downgrade to a cheaper Claude tier or finish from cache only. A runaway Claygent loop can burn real money before projection assumptions hold; enforce close to the action in the worker/provider_runner. Sources: https://www.baristalabs.io/blog/ai-agent-spend-circuit-breaker , https://markaicode.com/circuit-breakers-llm-api-reliability/

### Major bets (ranked)
1. **Route non-interactive AI columns through the Message Batches API (50% off)** — impact **high**, effort **M**. A `run_workbook` job is already async; collect its AI/conditional LLM requests into one batch (**up to 100,000 requests/batch** — corrected from the finding's 10,000), poll (<1h typical), write back per cell. Keep the synchronous path for interactive chat. Stacks with prompt caching (~95% combined). Sources: https://platform.claude.com/docs/en/build-with-claude/batch-processing , https://blog.imseankim.com/anthropic-claude-api-batch-processing-prompt-caching-cost-reduction-october-2025/
2. **Shard large workbooks into many small jobs (parallelism + per-workspace fairness)** — impact **high**, effort **M**. Fan a workbook into row-range sub-jobs (50–100 rows) on the same SKIP LOCKED queue + a finalizer; add a per-workspace in-flight cap so one tenant can't starve others. Today one big run hogs a replica while others idle (verified one-job-per-process). Turns the replica model into real horizontal throughput, keeping all crash/heartbeat/retry guarantees. Sources: https://www.netdata.cloud/academy/update-skip-locked/ , https://medium.com/@harsh.vaghela.work/postgres-is-the-only-queue-you-need-until-50k-jobs-sec-5931611b551c
3. **Semantic caching for free-text AI/research columns** — impact **medium**, effort **L**. Below the exact-key cache, an embedding cache (pgvector, reusing Postgres) serving cached answers above a cosine threshold; embed+search only on exact-miss; opt-in per column. Attacks the residual cost (similar-but-not-identical prompts) that caching/batching miss; reported 30–70% call reduction. Sources: https://arxiv.org/abs/2411.05276 , https://www.spheron.network/blog/semantic-cache-llm-inference-gpu-cloud/

## Deliberately NOT now / ToS-risky

- **Common Crawl bulk enrichment lake** — petabyte-scale egress/compute for a small team, stale (monthly) and sparse for the long tail that needs enrichment, and bulk-harvesting personal emails into a materialized store raises GDPR/CCPA controller liability. Defer until cheaper wins ship; revisit only with a narrow, lawful, domain-firmographic-only scope.
- **Opt-in crowdsourced/federated enrichment dataset** — recreates exactly the Apollo contributory-network model this roadmap markets *against*; domain-tied email patterns edge into shared personal-data processing needing a lawful basis; the "no SaaS can copy" moat claim is false (Clay/Apollo already run co-ops). High build cost, real compliance exposure, contradictory positioning. Drop.
- **Person-level website visitor de-anonymization** (the RB2B/Vector pattern) — identifying named individuals from anonymous EU/UK traffic without consent is legally dubious under GDPR/ePrivacy and increasingly challenged. Ship **company-level reverse-IP only**; never present person-level identification as a clean self-hosted win.
- **Scraping logged-IN or password-gated pages / fake accounts** — the exact conduct that sank hiQ. The escalation ladder must default to logged-OUT public pages; encode requires-auth = block-by-default.
- **GLEIF live API for bulk per-row resolution** — ~60 req/min/user cap. Not a feature to avoid, but a constraint: use the CC0 Golden Copy ingest for volume; reserve the live API for low-volume lookups.
- **OpenCorporates as a primary registry source** — now £2,250+/yr with a tiny free quota; prefer the keyless GLEIF/SEC/Companies House equivalents.
- **FlareSolverr** — deprecated, CAPTCHA solver non-functional as of Jan 2026; do not adopt. Use Solvearr/Byparr if a gateway is needed.
- **rebrowser-playwright / playwright-extra-stealth** — same detection failures as vanilla since Sept 2024 / abandoned. Use patchright.
- **Trusting raw SMTP RCPT for Gmail/Microsoft or catch-all domains** — they accept-all then bounce; never mark such addresses "valid." Route to confidence scoring instead.

## Dropped by skeptic (do NOT build)

- Common Crawl bulk enrichment lake (XL effort) — not illegal/ToS-dubious, but the effort/impact framing is hype for a small open-source team. Processing CC WARC/WAT/WET at useful coverage means petabyte-scale S3 egress/compute; emails/firmographics extracted are stale (monthly crawl) and sparse for the long tail that actually needs enrichment. The 'no proprietary SaaS can copy' claim is weak (Apollo/Clay already run co-ops). High build cost, real compliance exposure, contradictory positioning — drop or radically de-scope.

Keep company-level reverse-IP; discard/should-be-clearly-gated the person-level identification ambition rather than presented as a clean self-hosted win.
